# 别把 2B 当小号 GPT-4：llama.cpp + Qwen 2B 的六种实战玩法

在本地跑一个 2B 级别的模型（Qwen2.5-1.5B、Qwen3-1.7B 这一类），最常见的失望是「它连个像样的回答都给不出来」。于是很容易得出一个结论：小模型没用，还得上 32B 甚至 72B。

这个结论错在前提。**2B 的定位从来不是"小号 GPT-4"，而是流水线里一个廉价、快速、输出确定的专用零件。**

在一台普通笔记本上，Qwen 2B（Q4_K_M 量化）的生成速度可以轻松跑到 30 tokens/s 以上，显存占用不到 2GB。这意味着它一秒能吞下几十条请求。真正的技术含量不在于它有多聪明，而在于你**如何把任务切到它擅长的那一格**。

一句话概括本文的判断：**不要让小模型去"思考"，要让它去"填空"。**

---

## 先确认你的跑法

下文所有玩法都建立在 `llama-server` 上——它提供 OpenAI 兼容接口，任何现成的 SDK 都能直接接。一个够用的启动命令：

```bash
./llama-server \
  -m models/Qwen2.5-1.5B-Instruct-Q4_K_M.gguf \
  -c 4096 \
  -np 8 --cont-batching \
  --jinja \
  --host 127.0.0.1 --port 8080
```

几个参数值得单独说明：

| 参数 | 作用 |
|------|------|
| `-c` | 上下文长度，小模型不要盲目开大 |
| `-np` `--cont-batching` | 并行槽位 + 连续批处理，是批量吞吐的关键 |
| `--jinja` | 启用模型自带对话模板，工具调用能力依赖它 |
| `-ctk q8_0 -ctv q8_0` | KV Cache 量化，长上下文时能省一半显存 |
| `--mmproj xxx.gguf` | 加载视觉投影层，进入多模态模式 |

## 玩法一：语法约束输出器 —— 最高杠杆的一招

llama.cpp 原生支持 **GBNF 语法**与 **JSON Schema 约束解码**。这是它相对于 vLLM、Ollama 最显著的差异点，也是让 2B 从"勉强能用"跳到"近乎可靠"的关键。

原理并不复杂：解码时每一步都在候选 token 上做一次合法性过滤，只有能继续满足语法的 token 才允许被选中。**模型输出从概率问题变成了确定性问题。**

### 用 JSON Schema（推荐，最简单）

```bash
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [{"role":"user","content":"把这条日志转成结构化事件：2026-09-13 21:03 ERROR payment-service timeout after 3000ms"}],
    "response_format": {
      "type": "json_schema",
      "json_schema": {
        "name": "event",
        "strict": true,
        "schema": {
          "type": "object",
          "properties": {
            "level":   {"type": "string", "enum": ["INFO", "WARN", "ERROR"]},
            "service": {"type": "string"},
            "message": {"type": "string"}
          },
          "required": ["level", "service", "message"],
          "additionalProperties": false
        }
      }
    }
  }'
```

`strict: true` 会由服务端把 schema 编译成 GBNF，输出 100% 可解析。

### 用 GBNF 手写（适合非 JSON 的 DSL）

当你需要模型输出的不是 JSON，而是自定义 DSL、命令行或配置片段时，JSON Schema 就不够用了，得直接写语法文件 `schemas/idea.gbnf`：

```gbnf
root    ::= "{" ws "\"status\"" ws ":" ws status ws "," ws
                "\"tags\""   ws ":" ws taglist ws "," ws
                "\"summary\"" ws ":" ws str ws "}"
status  ::= "\"seed\"" | "\"researching\"" | "\"building\"" | "\"published\""
taglist ::= "[" ws (str (ws "," ws str)*)? ws "]"
str     ::= "\"" ([^"\\] | "\\" ["\\/bfnrt])* "\""
ws      ::= [ \t\n]*
```

启动时挂上：

```bash
./llama-server -m models/Qwen2.5-1.5B-Instruct-Q4_K_M.gguf \
  --grammar-file schemas/idea.gbnf
```

### 这一招能解锁的场景

- **文本 → 结构化事件**：日志、邮件、聊天记录按固定 schema 抽字段
- **自然语言 → 配置 / 命令 / DSL**：只填槽位，不自由创作
- **固定表结构下的 text-to-SQL**：表名和字段写进语法，直接杜绝表名幻觉
- **工具调用路由**：只输出一个函数名加参数，输出天然可执行
- **表单自动填充**：命中率远高于让大模型做长文本生成

## 玩法二：流水线调度员

把 2B 放在整条链路的**最前面**，让它做一次廉价判断，再决定后续走向。

- **意图分类 / 路由**：这条请求是闲聊、检索还是需要调用工具？本地秒出结论，需要时才升级到云端大模型。这一步能把云端调用量压掉一大截。
- **查询改写**：RAG 检索前先把用户口语化的提问改写成检索友好的查询，或生成假设性答案做 HyDE。
- **重排（rerank）**：召回 50 条候选，让 2B 按相关性排序取前 5 条，比直接全塞进大模型便宜一个数量级。
- **PII 检测**：在数据出机器之前，先用本地模型识别手机号、身份证、密钥并脱敏。

这类任务的共同点是**判断维度少、输出空间小**——恰好是 2B 的舒适区。

## 玩法三：上下文压缩器与本地守门员

这是最"划算"的用法之一：**长文档先用 2B 压成要点，再喂给大模型。**

一份 20K token 的文档，让 2B 分片压成 2K token 的要点，大模型只需要处理压缩后的内容。成本降低一个数量级，而要点提取这种"低阶理解"任务，2B 做得并不差。

另一方面，本地模型可以充当**守门员**：

- 提示注入检测
- 隐私与合规筛查
- 敏感内容拦截

数据不出本机，天然满足合规要求——这是云端 API 给不了的属性。

---

## 玩法四：离线批处理工人

用 `-np 8 --cont-batching` 起一个多并发的小服务，然后开跑批量作业：

- 给上千个文档自动打标、抽取元数据、生成摘要
- 提交信息、changelog、PR 描述生成
- 数据集清洗、去重、格式归一化
- 评论情感分类、工单自动归类

单条成本约等于零，跑一万条也只是电费。**「过夜跑批」是小模型最朴素也最被低估的价值。**

这里的吞吐量取决于并发而不是单条速度，所以并行槽位和连续批处理是必须打开的。

## 玩法五：投机解码的草稿模型

这是小模型价值最大化的一条路径，也是本文中最"有意思"的一种玩法。

原理：让小模型先连续猜若干个 token，大模型再用**一次前向**并行验证这批猜测。猜对的前缀直接接受，猜错的位置由大模型给出正确 token。

```bash
./llama-server \
  -m models/Qwen2.5-32B-Instruct-Q4_K_M.gguf \
  -md models/Qwen2.5-1.5B-Instruct-Q4_K_M.gguf \
  --draft-max 8 --draft-min 2 --draft-p-min 0.7 \
  -c 8192 -ngl 99
```

其中 `-md`（`--model-draft`）指定草稿模型，`--draft-max` 控制单轮最多猜多少 token。

关键在于：**验证是一次前向，而逐 token 解码需要 N 次前向。** 如果草稿命中 3 个，一次前向就产出了 4 个 token。实测在 Qwen 系列上可以获得 2～3 倍的端到端提速，而且**输出分布与大模型完全一致，不损失质量**——这是它相比各种剪枝、蒸馏手段最大的优势。

草稿模型不需要很聪明，只需要**快**。2B 恰好满足。

## 玩法六：LoRA 热插拔与多模态

### LoRA 热插拔：一个 base，多套人格

llama.cpp 支持运行时切换 LoRA 权重，不必重启进程：

```bash
./llama-server -m models/base.gguf \
  --lora adapters/style-a.gguf \
  --lora-init-without-apply
```

之后按请求切换：

```bash
curl -X POST http://127.0.0.1:8080/lora-adapters \
  -H "Content-Type: application/json" \
  -d '[{"id": 0, "scale": 1.0}]'
```

一个 2B base 模型可以同时服务"正式文风""口语化""结构化抽取"等多套 adapter，按请求热切换。训练成本极低，是个人开发者压榨小模型的实用技巧。

### 多模态小模型：本地截图理解

换成视觉模型加 `--mmproj`，本地就能做截图理解、图表转数据、票据抽取：

```bash
./llama-server \
  -m models/Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf \
  --mmproj models/mmproj-Qwen2.5-VL-3B-f16.gguf
```

再配合玩法一的语法约束，可以直接把图片内容落进数据库。

### 多实例与多机

- 起多个 `llama-server` 实例、各挂不同 grammar，组成一个"微服务矩阵"
- 用 `rpc-server` 把几台闲置旧机器拼成一个小推理池，压榨存量硬件

## 能力红线：什么不该交给 2B

| 判断 | 任务类型 |
|------|----------|
| ✅ 放心用 | 分类、抽取、改写、摘要、打标、语法约束输出、重排、路由 |
| ⚠️ 必须加约束 | 工具调用、SQL、JSON、DSL 生成 |
| ❌ 别碰 | 多步推理、数学计算、长链 Agent 规划、开放域事实问答、长文档全局理解 |

一个常被忽略的坑：**2B 标称 32K 上下文，但有效上下文通常只有 4～8K**，超出后性能断崖式下跌。批处理时务必分片。

另外几个实践建议：

1. **温度调低**。做分类和抽取时用 `temperature: 0`～`0.3`，2B 在高温下非常容易跑偏。
2. **语法约束不要滥用**。它锁死输出空间，需要自由文本生成的场景会适得其反。
3. **不要把 2B 当知识库**。它没有足够的参数容量承载事实，凡涉及事实的内容一律走检索或升级到大模型。
4. **认准它的长处是延迟与成本，不是智力**。省下来的钱和延迟，才是引入它的理由。

## 总结

小模型的正确使用姿势，是把它当成**系统里的一个零件**，而不是一个"更弱的助手"。

一旦接受这个前提，路径就很清晰了：

- **约束它的输出**（GBNF / JSON Schema）——让不可靠的模型产出可靠的结果
- **限制它的任务**（分类、抽取、改写、重排）——只让它做判断维度少的事
- **放大它的速度**（批处理、投机解码、LoRA 热插拔）——把"便宜"和"快"变成系统优势

2B 不会替你思考，但它可以让你的系统更快、更便宜、更私密。这已经足够值得在本地跑起来了。
