## 问题的本质

多 Agent 系统在企业落地时，最常见的误区是：先跑起来再说，权限和安全以后补。

但现实是——当 Agent 开始调用数据库、写文件、操作生产系统时，权限设计就不是可选项了，而是生死线。

## 权限隔离：从共享沙箱到命名空间

### 最小权限原则

每个 Agent 应该只拥有完成其职责所需的最小权限。这听起来简单，但在 Agent 框架中实现却不容易，因为 Agent 的 Tool 调用往往是动态的——一个对话内，Agent 可能调用 3 个不同的 Tool，每个 Tool 的权限边界不同。

### 实操方案

**1. 命名空间隔离**

每个 Agent 运行在独立的逻辑命名空间中，Namespace 决定了：
- 能访问哪些 Tool
- 能读写哪些数据源
- 能调用哪些外部 API

**2. RBAC + ABAC 双层校验**

- **RBAC（角色级）**：定义 Agent 的角色（如"只读分析员"、"写操作员"、"管理员"）
- **ABAC（属性级）**：在每次 Tool 调用时，检查调用者的属性（时间、IP、来源上下文、风险等级）

双层校验的关键在于：RBAC 划定范围，ABAC 做实时决策。单纯 RBAC 会导致权限过粗，单纯 ABAC 则管理成本过高。

**3. 人工确认网关**

对于涉及敏感操作（如写入数据库、发送邮件、执行命令）的 Tool 调用，设计一个"人工确认"中间层。Agent 发出请求 → 等待人工确认 → 放行或拒绝。这个机制在高风险场景中是不可或缺的，也是用户信任 Agent 的基础。

## 风险治理：全链路可观测性

### 护栏模型（Guardrails）

Guardrails 不是简单的关键字过滤，而是部署一个专门的"Agent 监控 Agent"，实时审查：
- 输入侧：是否包含 Prompt Injection 或越狱尝试
- 输出侧：是否泄漏了敏感数据、是否产生了不安全的指令序列

### 熔断与限流

Agent 的 Tool 调用可能存在循环依赖或资源耗尽风险。应当为每个 Agent 设置：
- 单次会话最大 Tool 调用次数
- 单次调用超时时间
- 全局并发调用上限

### 全链路审计日志

每一条 Agent 决策路径都必须有迹可循。审计日志至少包含：
- 谁调用了什么 Tool（Agent 身份 + 用户身份）
- 调用参数是什么
- 返回结果是什么
- 决策耗时和成功率

## 总结

企业 AI 的安全不在于限制 Agent 的能力，而在于建立一套可控、透明的运行环境。权限隔离和风险治理，是 Agent 从"玩具"走向"生产工具"的核心门槛。
