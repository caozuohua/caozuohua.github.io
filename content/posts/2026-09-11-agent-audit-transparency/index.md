在 AI Agent 的落地场景中，随着 Agent 承载的业务逻辑日益复杂，如何确保其行为的可审计性成为了企业级应用的关键。一个常见的误区是试图通过让模型“自我解释”或直接在工具逻辑中添加追踪标记来审计。

本篇博客探讨如何通过架构解耦，构建一个轻量、防篡改且不干扰模型执行的 Agent 审计框架。

### 1. 为什么审计逻辑不能内置于工具？

在早期的设计尝试中，我们曾考虑在每个工具（Tool）函数内部添加日志记录逻辑。但很快发现这种做法存在以下问题：

*   **代码耦合度高**：工具本身的职责是执行任务，审计职责的增加会破坏单一职责原则。
*   **一致性难以维护**：随着工具库的扩展，审计逻辑的碎片化会导致不同工具的日志格式不统一。
*   **难以防御篡改**：如果审计逻辑由被审计对象（工具/模型）直接维护，恶意调用可能会通过覆盖日志来掩盖踪迹。

### 2. 审计框架的核心设计原则

我们建议将审计框架与执行逻辑物理分离，采用 “Dispatcher 拦截模式”：

*   **执行与审计物理隔离**：所有的审计信息由底层的 Dispatcher（调度器）负责记录，而不由 LLM 直接参与生成或维护。这从根源上消除了模型幻觉干扰审计日志的可能。
*   **上下文无感注入**：在请求到达系统的一瞬间，框架为该行为链分配唯一的 TraceID。在调用工具前，Dispatcher 负责将 TraceID 像“补丁”一样注入调用参数。
*   **结构化元数据存储**：不要将审计标记嵌入 Markdown 或模型输出的正文，而是将其作为元数据（Metadata）存储在结构化数据库中。

### 3. 如何防范 LLM 幻觉干扰？

对于“模型是否会伪造审计标记”的担忧，我们采用以下验证机制：

1.  **确定性分配**：由框架代码负责 ID 生成，LLM 仅作为无状态的执行引擎，对 TraceID 的生成过程不可见、不可控。
2.  **不可逆日志哈希链**：在审计日志写入时，引入哈希链（Hash Chain）。每一条行为日志的 Hash 都包含上一条日志的 Hash。由于 LLM 无法预测后续 Hash 值，它在事后即便试图篡改记录也无法通过校验。

### 4. 未来展望

Agent 的透明度不是为了限制它的行为，而是为了让开发者在复杂多变的 AI 应用场景中，始终能保持“可控感”。通过将审计层下沉到架构底层，我们将能把更多的资源投入到更高级的决策优化中。
