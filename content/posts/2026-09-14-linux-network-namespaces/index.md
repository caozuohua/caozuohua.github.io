# 沙箱的屏障：深入解析 Linux 网络命名空间与容器隔离

在容器化时代，网络不再只是简单的物理网卡通信，而是通过 Network Namespaces (NetNS) 构建的虚拟化网络空间。对于需要处理多租户、复杂内外网流量的企业级 Agent 系统，理解这一屏障至关重要。

## 网络命名空间：逻辑隔离的基石

每一个网络命名空间都拥有一套完整的网络协议栈：独立的网卡、IP 地址、路由表、防火墙规则。

*   **veth pair**：连接命名空间的“桥梁”，一端插入 NetNS，另一端连接宿主机的网桥 (Bridge)。
*   **Bridge (网桥)**：充当虚拟交换机，实现同一宿主机下不同命名空间的通信。
*   **iptables/netfilter**：通过 NAT 和转发规则，控制容器与宿主机、容器与互联网之间的流量。

---

## 企业级 Agent 的“网络痛点”与隔离设计

在设计 Agent 时，我们不仅要让它“联网”，更要实现“受控的隔离”。

### 1. 复杂环境下的隔离策略
*   **租户间流量切断**：利用不同的 NetNS 为每个租户 Agent 分配独立的虚拟网卡，通过宿主机 Bridge 的 ACL 规则彻底隔离租户流量，防止横向探测。
*   ** egress 出口管控**：在容器命名空间内设置统一网关，强制所有出站流量必须经过 Agent 统一治理网关（Proxy/WAF），进行行为审计与流量清洗。

### 2. 流量调试与可观测性
在复杂网络环境下，Agent 经常遇到“请求发不出去”或“响应超时”，如何快速定位？

*   **“旁路探测”**：在容器内注入 `tcpdump` 或 `mitmproxy`，通过 Unix Domain Socket 将抓包数据实时流转至外层 Agent 的治理工具链中，而非直接在容器内执行调试命令。
*   **全链路追踪**：在 Agent 发起请求的协议层（如 HTTP Request Header）植入 `X-Trace-ID`，通过宿主机侧的 `eBPF` 工具监听网络流量，实现从容器内到宿主机的全链路流量关联。

## 实践：Agent 层的网络调试架构

不要在生产容器里进行危险的操作。推荐方案：

1.  **调试 Sidecar**：将 `net-tools` 封装在专门的 Debug Sidecar 容器中，动态 attach 到目标 Agent 的 NetNS。
2.  **配置驱动调试**：通过 MCP 工具层，远程调用宿主机 eBPF 探针，直接读取内核态网络堆栈状态，这种方式无需改变业务进程权限，对生产环境侵入性最小。

```bash
# 示例：查看宿主机上属于某个容器的 NetNS
ip netns list
# 示例：通过 NetNS 进入容器进行网络探测（需具备对应能力）
nsenter -n -t <PID> ip addr
```

## 总结

网络隔离是 Agent 安全的第一道防火墙，而透明化的网络调试是保障 Agent 稳定性的基石。在企业级落地中，通过 **eBPF 观察技术 + Sidecar 调试模式**，我们可以在不牺牲隔离性的前提下，获得极高的故障排查效率。
